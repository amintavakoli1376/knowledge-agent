# ADR-0001: نگهداری متن کامل محتوا در SQLite کنار Notion

**وضعیت:** ✅ پذیرفته‌شده (Accepted)  
**تاریخ:** 8 آگوست 2026  
**تصمیم‌گیرنده:** Amin Tavakoli  
**نویسنده:** Hermes Agent  

---

## Context (بستر)

Knowledge Agent محتوا را از ۸ منبع (ArXiv, وب‌سایت، YouTube، Twitter، Instagram، LinkedIn، Telegram، PDF) استخراج می‌کند، با AI خلاصه می‌سازد و در **Notion** ذخیره می‌کند.

محدودیت‌های فعلی:
- Notion فقط خلاصه (۳۰۰ کاراکتر) + متادیتا را نگه می‌دارد — **متن کامل دور ریخته می‌شود**
- برای RAG / جستجوی برداری آینده، متن کامل لازم است
- استخراج مجدد همه لینک‌های گذشته غیرعملی است (هزینه + زمان + احتمال شکست)

## Decision (تصمیم)

متن کامل استخراج‌شده را در **SQLite** (فایل `data/knowledge.db`) ذخیره می‌کنیم، کنار Notion:

```
ورودی → extractor → متن کامل
                        ├──→ SQLite (تب content + FTS5) ← متن کامل + متادیتا
                        └──→ Notion (خلاصه + لینک + تگ) ← نمای کاربر
```

صفات اجرایی:
- جدول `content`: url (unique)، title، platform، full_text، author، metadata (JSON)، saved_at
- ایندکس **FTS5** برای جستجوی تمام‌متن (با trigger های هماهنگ)
- ذخیره **best-effort**: خطای SQLite هرگز پایپ‌لاین Notion را نمی‌شکند (try/except)
- در هر دو مسیر فراخوانی می‌شود: `api_save` (REST) و `handle_message` (Telegram bot)

## Alternatives (گزینه‌های ردشده)

| گزینه | چرا رد شد |
|-------|----------|
| ذخیره در خود Notion (بلاک چایلد) | محدودیت ۱۰۰ بلاک/صفحه، کند، جستجوی ضعیف |
| فقط خلاصه (وضعیت فعلی) | متن برای RAG آینده از بین می‌رود |
| S3/میزبان فایل | اضافی برای حجم فعلی؛ SQLite کافی است |
| PostgreSQL | سنگین برای سرور ۱GB رم؛ SQLite برای این مقیاس بهینه |

## Consequences (پیامدها)

**مثبت:**
- ماده اولیهٔ RAG / embedding برای همیشه محفوظ است
- جستجوی تمام‌متن رایگان (FTS5) بدون زیرساخت اضافه
- حجم سبک: ~8MB در هر ۱۰۰۰ مقاله — مناسب سرور فعلی (1.5GB آزاد)
- بدون وابستگی خارجی جدید (SQLite استاندارد پایتون)

**منفی/ریسک:**
- دیتابیس روی دیسک تک سرور؛ نیاز به بکاپ (در cron بکاپ اضافه شود)
- فایل‌لوک/همزمانی: تراکنش‌ها کوتاه و سبک هستند، در مقیاس فعلی مشکلی نیست
- اگر بعداً باید multitenant شود (تجاری‌سازی)، ممکن است به Postgres مهاجرت کنیم

## وضعیت آینده

- فاز RAG: متن کامل ← چانک ← embedding (API، نه مدل محلی) ← Qdrant/Chroma
- تجاری‌سازی: جدول per-user (`user_id` ستون) در نسخه چندکاربره

## پیوست: چرا PRD قبل از ADR؟

| PRD | ADR |
|-----|-----|
| مشخص می‌کند «کاربر چند منبع را ذخیره کند، خلاصه فارسی بخواهد» | تعیین می‌کند «متن کامل را کجا نگه داریم» |

ترتیب درست: **PRD → ADR → کد**. PRD لازمهٔ قبل از ADR چون بدون نیاز محصول، تصمیم فنی بی‌معناست. برای پروژهٔ Knowledge Agent، PRD تجاری‌سازی باید پیش از ADRهای بعدی (Multi-user, Billing) نوشته شود.
